# ANANKE | Public product roadmap

**Last reviewed: 24 November 2026.** This roadmap separates completed historical research milestones, the current critical path, conditional commercial delivery and longer-horizon concepts. **No dates, release windows or availability are promised.** A checked item denotes only the stated evidence class—not production certification.

## North-star

**Build infrastructure that determines whether fresh intelligence must be spent, preserves independently valid prior work, escalates genuine novelty, and lets customers verify quality and net economics.**

## Unified product acceptance doctrine · 25 November 2026

The required final journey is **normal authorized BYOK request → real ANANKE entrypoint → canonical governed runtime → valid deterministic answer / eligible Capital reuse / necessary provider execution → verified response → durable receipt → original customer surface and scoped dashboard**. The native engine test is necessary but **not** a substitute for the customer ingress-to-output test. [Permanent acceptance and anti-drift contract](docs/end-to-end-north-star-and-continuity-contract.md). External beta still **NO-GO**.

## 24 November candidate engineering dependency update

The current EngineOnly route has been traced separately from customer-pilot onboarding; existing Capital/custody mechanisms and the new opt-in read-only SQL path can be reused. These are **offline/component** milestones. The next engineering ordering is: legitimate product eligibility and scoped source/provider execution → native engine A/CONTROL/B/CHANGE/C and matched economics → authenticated Website/BFF customer receipts and dashboard readback. These remain dependencies **within P0/P1**, not newly invented launch phases. [Evidence cutoff and gates](docs/integration-checkpoint-2026-11-24.md).

## P0 — Integrated customer truth (critical path)

**Outcome required:** one authorized, genuinely executed customer journey with authoritative request, receipts and usage—rather than a simulated dashboard or a chain of isolated offline tests.

- [x] Develop historical local control-plane and product interfaces for projects, provider setup, requests, receipts and dashboards. **Historical component/local milestones.**
- [x] Publish controlled local-model and external-provider research, including adverse results.
- [x] Qualify M06 one-tier policy candidate in focused offline checks.
- [ ] Demonstrate actual independently authorized customer identity and customer/project mapping in a contained native session.
- [ ] Execute the existing website/application boundary into the governed runtime with durable authoritative receipt and scoped dashboard readback.
- [ ] Verify cross-project denial, rights isolation, credential revocation, recovery and controlled teardown.
- [ ] Obtain one current, coherent integrated acceptance record rather than reusing historical local PASS labels.

**As of 24 November:** P0 remains **open**, customer E2E NOT PROVEN; external beta **NO-GO**.

## P1 — Model-backed Computational Capital and value truth

**Outcome required:** demonstrate that ANANKE preserves correct capability while reducing unnecessary model work in a real representative workflow.

- [ ] Prove at least one **genuinely model-necessary** governed task with actual provider execution and raw usage accounting.
- [ ] Issue eligible, independently supported Computational Capital and validate correct reuse by another request.
- [ ] Change the authoritative source and prove affected invalidation with an unaffected control.
- [ ] Compare baseline and governed execution on matched tasks, including all provider calls, input/output tokens, cost, latency, retries and ANANKE governance overhead.
- [ ] Freeze acceptance thresholds for quality, false reuse/suppression and **net** economic benefit; record FAIL when unmet.
- [ ] Read the same evidence back through the existing customer dashboard without fixture-only values.

**Gate:** no production savings promise before actual customer-value proof.

## P2 — Developer and design-partner usability

**Outcome required:** a supportable integration path for a narrow, validated product offering.

- [ ] Stabilize the publicly supported request and receipt contracts after internal acceptance.
- [ ] Publish rights-cleared onboarding, compatible developer SDK documentation and quickstarts only when interfaces are approved.
- [ ] Qualify a small set of clearly versioned repeatable workloads as pilot reference classes.
- [ ] Validate observability, debugging, rollout controls, user-facing denials, and escalation when reuse is unsafe.
- [ ] Evaluate customer willingness to pay and supported pricing/package hypotheses using real use.
- [ ] Invite a bounded set of design partners **only after** applicable privacy, security and operational gates.

## P3 — Enterprise and operational qualification

**Outcome required:** commercially supportable infrastructure with formal operational boundaries.

- [ ] Independent security and isolation assessment, credential and key-lifecycle testing, access reviews.
- [ ] Reliability, recovery, incident response, data retention and audit export policies.
- [ ] Supported provider/interoperability matrix with measured cost and performance.
- [ ] Operational monitoring, service-level objectives, deployment/hosting qualifications and escalation support.
- [ ] Legal, privacy, licensing, patent and freedom-to-operate review where necessary.
- [ ] Controlled private beta and later general availability **only when release gates pass**.

## P4 — Longer-term conditional product expansion

These are **research/product options, not shipping commitments**.

| Expansion area | Product hypothesis | Qualification needed |
| --- | --- | --- |
| More intelligence tiers | Additional small, specialized, local and frontier executors | Task-specific correctness and governance gates |
| Broader workflow adapters | Support for more agent frameworks, document systems and enterprise workflows | Secure contract and integration compatibility |
| Long-lived Capital portfolios | More reusable, evidence-backed work across repeated permitted workflows | Cross-time validation, privacy and rights controls |
| Advanced change management | More fine-grained source freshness and invalidation | Proven no stale or unauthorized reuse |
| Multi-region and enterprise deployment | Controlled hosted/hybrid operations | Operational, security and tenancy acceptance |
| Economics and policy intelligence | Better customer budgeting and counterfactual reporting | Reconciled measured vs estimated usage |
| Specialized model research / Foundry | Optional future development or evaluation of narrow executors | Independent quality, efficiency, cost and commercialization evidence |
| External research replication | Publication of sufficiently rights-cleared benchmark fixtures | Independent reproduction and documented validity bounds |
