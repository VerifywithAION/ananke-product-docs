# Where ANANKE could create value

**The scenarios below are prospective product use cases, not claims of live enterprise customers or deployed installations.** Their value must be tested under real sources, permissions and changing conditions.

## Use-case portfolio

| Workflow | Repeated obligation | When fresh work remains necessary | Candidate business value |
| --- | --- | --- | --- |
| Enterprise support | Classify routine cases against an approved policy | Policy changes, ambiguous cases, new issue types | Lower repetitive decision work; auditable escalation |
| Compliance operations | Re-check established documents against governed rules | New regulation, revised evidence, changed identity or scope | Preserve validated work without re-reviewing everything |
| Developer agents | Re-analyze unchanged repository context | New commit, changed dependencies, novel code issue | Avoid redundant analysis while preserving source correctness |
| Research assistants | Re-run recurring searches and structured checks | New evidence, changed question, missing provenance | Reuse durable validated findings |
| Finance operations | Recompute recurring standardized classifications | New transaction facts, exceptions or changed policy | Controlled repetitive decision cost |
| Document ingestion | Repeat extraction/classification for unchanged sources | New version, new field requirements, low confidence | Measurable repetition reduction |
| IT operations | Re-evaluate known incidents and runbooks | New telemetry, changed infrastructure, high-risk response | Less redundant diagnosis |
| Sales enablement | Re-check recurring catalog or eligibility questions | New prices, contracts or customer entitlements | Faster authorized responses |
| AI evaluation pipelines | Repeat validations for unchanged test inputs | Changed model, rubric, data or policy | Avoid unnecessary re-evaluation |
| Multi-agent systems | Agents revisit already resolved subtasks | New dependency, incompatible source or policy | Control compute amplification across agents |

## Three pilot wedges worth testing first

### 1. Policy-backed customer-support classification
**Buyer hypothesis:** head of support operations or AI-platform owner. **Why test:** repeated structured queries, explicit source versions and easy-to-measure correctness. **Primary metrics:** justified inference rate, false suppression, escalations, net cost per resolved obligation and p95 latency.

### 2. Document validation under version changes
**Buyer hypothesis:** enterprise operations/compliance leader. **Why test:** source-change events and verifiable evidence boundaries create a measurable distinction between safe and unsafe reuse. **Primary metrics:** valid repeat coverage, stale-result prevention, re-computation after change, manual review rate and audit quality.

### 3. Agent development workflows
**Buyer hypothesis:** AI-infrastructure and engineering teams. **Why test:** repeated context and version-controlled dependencies may expose whether conditional reuse adds value beyond prompt caching or repository caches. **Primary metrics:** real provider calls, total token usage, task correctness, invalidation misses, latency and overhead.

## Example: why a semantic match is not enough

A service case on Monday has the same wording as a request on Thursday. The source policy changed on Wednesday. Similarity-based retrieval might propose Monday's decision; an evidence-governed system must establish whether it remains valid and authorized, otherwise it should escalate to fresh evaluation.

This is an example of the **intended behavior**, not a published claim that arbitrary policy corpora are already connected.

## Qualification checklist for each pilot

A commercially defensible pilot would preregister its baseline, source authority, input mix and novelty; include both repeated and genuinely novel tasks; test rights and policy isolation; run forced drift and contradiction cases; account for *all* model calls and ANANKE overhead; measure quality and false reuse; and compare net economics over a representative window.

**No workflow is accepted merely because it shows a high cache-hit or avoided-call percentage.**
